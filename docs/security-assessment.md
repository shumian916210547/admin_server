# 安全与维护评估

## 结论

本项目不适合直接让浏览器继续连接 Parse Server。完全重写为全新的业务后端会带来较高迁移风险和维护成本，因此采用渐进式的 **BFF（Backend for Frontend）** 架构：保留 Parse Server 作为仅内网可访问的数据引擎，由 Express BFF 统一处理认证、授权、租户隔离、文件访问和审计边界。

这在不重写现有动态表单/动态路由能力的前提下，消除了浏览器掌握主密钥和直接访问数据库 API 的核心风险；未来替换 Parse 时也只需要替换 `services/` 层，而不是重写前端。

## 改造前的主要风险

| 风险 | 影响 | 状态 |
| --- | --- | --- |
| 浏览器配置中出现 Parse 主密钥、服务地址和 Dashboard 地址 | 任意访客可绕过前端权限，直接读写数据或管理结构 | 已移除 |
| Parse REST/Dashboard 对公网暴露 | 增加暴力破解、已知漏洞和误配置攻击面 | 已隔离至 `127.0.0.1:1337` |
| 前端传入 `companyId` 决定查询范围 | 可造成跨租户读取与修改 | BFF 从签名会话解析租户 |
| 前端 ACL/按钮权限作为主要控制 | 可被直接构造请求绕过 | 服务端 RBAC 与类级私有权限接管 |
| 上传使用用户文件名和宽泛 MIME 判断 | 可形成同源存储型 XSS、路径和缓存问题 | 已使用精确白名单、服务端后缀与私有响应头 |
| MiniApp 代码保留硬编码凭据与固定密码 | 凭据泄露和撞库风险 | 已环境变量化、派生凭据且默认关闭 |

## 当前安全边界

- 浏览器只访问 `/api`，会话使用 `HttpOnly`、`SameSite=Strict` Cookie；写操作必须带 CSRF Token。
- 仅 BFF 可以使用 Parse Master Key；Parse Server 和 Dashboard 不对公网路由。
- 租户范围由服务端会话确定，管理员读取文件也必须属于同一公司。
- 通用数据接口会校验写入的指针对象仍在本租户内；嵌套用户对象会移除敏感字段。
- 动态建表只允许管理员操作自定义业务表，平台系统表和租户字段不可由通用接口修改或删除。
- 上传文件采用精确 MIME 白名单、随机文件名、服务端生成后缀、`nosniff`、私有无缓存响应头；非媒体文件强制下载。
- MiniApp 兼容路由默认禁用；若将来启用，租户和身份只能来自服务器配置。多租户 MiniApp 必须先实现独立的服务端成员关系解析器。

## 维护成本变化

- 安全控制由前端各页面和 Parse ACL 分散维护，收敛到 BFF 的认证、中间件与 `parse-data.service.js`；新增功能只需复用统一 API 规则。
- 前端保留了兼容适配层，原有生成式页面不需要整体重写；同时移除了浏览器 Parse SDK、XLSX 和富文本编辑器等不必要依赖。
- CI 会执行构建、安全静态检查和生产依赖审计，能在合并前阻止主密钥、直连 Parse 和高危依赖回归。

## 上线前必须完成的操作

1. 将历史上出现过的数据库口令、Parse App ID/Master Key、JWT 密钥、微信凭据和 TLS 私钥全部吊销并重新生成；不要只修改仓库中的文件。
2. 备份 PostgreSQL，配置最小权限的数据库账号，在受控终端运行 `npm run security:harden` 收紧既有 Parse 类权限。
3. 生产反向代理仅发布前端静态站点和 BFF 的 `3000` 端口；不要暴露 `1337`，不要把 Dashboard 挂到业务域名。
4. 生产环境设置强随机 `.env` 值，并在部署后执行 `npm run security:check`、`npm run check` 和 `npm run audit:prod`。

## 已知残余

生产依赖审计当前没有 high 或 critical 漏洞。Parse Server 的未启用推送适配器链仍报告 11 个 moderate 漏洞；该链不配置推送服务、也不通过公网暴露。不要为了消除该提示执行会将 Parse Server 降级的 `npm audit fix --force`；应在 Parse Server 发布兼容修复后常规升级并重新审计。

本地 PostgreSQL 当前未运行，因此本次没有对真实数据执行 CLP 收紧或做数据库集成测试；上线前的备份、密钥轮换和 `security:harden` 是不可跳过的运维步骤。
